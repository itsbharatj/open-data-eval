1. **R2R-CE test episodes are already public on GitHub.** I found this independently; it agrees with A1 v2, which was updated concurrently and corrected A1 v1's "no public mirror". `YicongHong/Discrete-Continuous-VLN` (main, commit 2aa38fa, 2023-10-31) ships `data/datasets/R2R_VLNCE_v1-2_preprocessed/test/test.json.gz`. HA-R2R episode IDs equal R2R-CE IDs for every split: identical ID sets, including train's 18 missing IDs (1137-1139, 2837-2839, …). The public per-episode `collision_num_*` is constant within every R2R-CE trajectory (0 inconsistencies over 3,603 train trajectories, including 10 four-instruction ones, against ~760 for a random permutation and 2 for a shift of 3). So **each HA-R2R test episode can already be mapped to its R2R path, start viewpoint and three original instructions**. The within-trajectory order matches R2R `instructions[0,1,2]` in 1,136/1,136 blocks, and the R2R-CE test trajectory order is NOT ascending by path_id (571/1,135 ascending pairs; A1 v2 also finds that test is grouped in scene blocks while train/val are sorted).
2. **Public room-type labels for 76% of test-scan viewpoints, no MP3D approval needed.** `niessner/Matterport` `tasks/region_classification/data/test_room_pano_{image,label}.txt` labels 1,539 panoramas of exactly the 18 R2R test scans (MP3D benchmark test split = R2R test split; val = R2R val_unseen; train = R2R train) with 12 region classes. The integer ids are not documented. I decoded them by cross-tabulating against HA-VLN 2.0 human categories, with 95–100% purity per class: 1 office, 2 lounge, 3 familyroom, 4 entryway/foyer/lobby, 5 dining room, 6 living room, 7 stairs, 8 kitchen, 9 porch/terrace/deck (also takes 'outdoor'), 10 bathroom, 11 bedroom, 12 hallway. Coverage is 1,501/1,971 included test viewpoints (two scans, gYvKGZ5eRqb and gxdoqLR6rwA, have 0) and 903/1,136 test start viewpoints. An unlabelled viewpoint usually sits in a non-12 room type (closet, toilet, balcony, other room, tv, meeting, spa, …): on public 2.0 humans, 92–99 of the 122 whose anchor viewpoint is unlabelled carry a non-12 category (75–81%).
3. **Public object landmarks for 100% of test-scan viewpoints.** `YuankaiQi/REVERIE` `tasks/REVERIE/data/BBox/<scan>_<vp>.json` has 10,567 files covering all 90 scans and all 1,971 included test viewpoints. Each file lists MP3D house-object ids, raw category names, which of the 36 R2R discrete views see the object (within 3 m), and 2-D boxes. That is 3,368 distinct visible objects in the test scans, 0.1–7.4 per viewpoint; it is very sparse in gYvK/gxdo/fzyn/WYY7. `REVERIE_test.json` adds 2,304 extra object-goal instructions whose (scan, start, heading) all match R2R test paths; 176 of the 1,136 CE-test trajectories match unambiguously.
4. **`human_motion_text.json` value = [`"<MP3D region name>:<activity>"`, SMPL/MDM model id ∈{0,1,2}, heading in integer degrees]**, from GUI.py L155-157, fine_tune_heading/GUI.py L91-97/L218-220 and get_info.py L78-97/L118-131. The human sits at the viewpoint's (x,y) on the floor (z−1.36 offset in the renderer) and is rotated about the vertical axis. The 18 test scans hold 70 HA-VLN 1.0 humans. As a prior for 2.0 placements it is weak: on the 72 public scans only 35% of 2.0 humans are anchored at a 1.0 viewpoint, 82% of 1.0 viewpoints survive as 2.0 anchors, 2.0 humans sit a median 1.06 m (p90 4.2 m) from their anchor viewpoint, and the 1.0 region text agrees with the MP3D label only 39–51% of the time. HA-VLN 2.0 categories, by contrast, match MP3D region labels ~95%.
5. **The goal is a discrete nav-graph node, and room type cuts the candidate set ~6×.** On R2R train, the nodes 3–6 hops and 5–25.5 m from the start number median 28. Keeping only those with the goal's room label leaves median 4 (ratio 0.17). Pooling the three original instructions, 59% of paths name the goal room type in the last 40% of at least one instruction (71% anywhere; crude keyword lists, so a lower bound). For test trajectories: median 25 candidates, mean 24.0 of 28.9 region-labelled. [COMPLIANT use: a room-type head trained on TRAIN-scan labels plus this prior; OFFLINE-ONLY use: the test labels themselves.]
6. **MP3D semantics with standard access:** `mp3d_habitat.zip` (download_mp.py `--task_data habitat`) has `<scan>.glb`, `<scan>.navmesh`, `<scan>.house`, `<scan>_semantic.ply` per scan. The `.house` file has levels (L), regions (R: label code, AABB, height), portals (P: region0↔region1 spans, which give door/room adjacency), surfaces+vertices (S/V: CCW floor polygons), **panoramas (P name=viewpoint id → region index: an exact viewpoint→room map)**, images (I), categories (C: raw + mpcat40) and objects (O: OBB + category). habitat-sim 0.1.7's `loadMp3dHouse` parses only H/L/R/C/O/E (it skips panoramas, portals and polygons), applies the z-up→y-up rotation, and renames 3 region classes. Use a custom parser for viewpoint/region/portal data.

## 2. `human_motion_text.json` (HA-VLN 1.0): what the ints mean
File: `BASE/HA-VLN/HASimulator/HA-DE/human-viewpoint_annotation/human_motion_text.json`; 90 scans, 374 humans, keyed scan → viewpoint id → `[text, int, int]` (types str,int,int for all 374).
- `text` = `"<region>:<activity>"`. `<region>` is one of the 29 MP3D region names written as in data_organization.md (e.g. 'familyroom', 'porch/terrace/deck/driveway', 'outdoor areas containing grass, plants, bushes, trees, etc.'). These are chosen from the combo box filled by `region_motion_text.json` (29 regions × 5 activities = 145 prompts = `HA-VLN_human_motion_prompts.txt`, 144 lines) (human-viewpoint_annotation/GUI.py L38-42, L155). Because annotators picked the region by hand, it agrees with MP3D's true region label for only 51% (test, n=53) / 39% (non-test, n=209) of labelled viewpoints (`S/a9_scripts/regcls.py` + inline check).
- `int #1` = **3-D human model id ∈ {0,1,2}** = the MDM repetition index (`sample{motion:02d}_rep{model:02d}.mp4`, GUI.py L43, L48, L156; mesh dir `human_motion_meshes/<text with ' ' and '/' → '_'>/<model>_obj`, get_info.py L56, L84). Distribution 0:140, 1:146, 2:88.
- `int #2` = **human heading in integer degrees** about the vertical axis. It starts at 0 on save (GUI.py L157/L161) and is later tuned with a 0–360 dial (fine_tune_heading/GUI.py L91-97, L218-220, saved L306-308). It is applied as `getRotation(theta=pi/180*heading)` about the renderer's +y (up) axis (get_info.py L100-108, L119-131; rendermdm.py L57-60). Range 0–357; 100/374 are still 0, i.e. never tuned.
- Position = the viewpoint's connectivity pose translation (pos_info), placed at `(x, z−1.36, −y)` in renderer coordinates (get_info.py L118; rendermdm.py L52, L90). In `tasks/HA/data/human_locations.json` the test-scan humans' frame-0 xy sits a median 0.08 m from the viewpoint, and they move a median 0.55 m (max 9.49 m) over 120 frames.
- The human count per scan was seeded by `humanNum = n_viewpoints*2//67 + 1` (GUI.py L388-391); 83/90 scans match exactly.
- The 70 test-scan humans (2–7 per scan) are listed with region, activity, model, heading and MP3D xyz in `S/a9_out/humans.txt`.

HA-VLN 2.0 (`Data/Multi-Human-Annotations/human_motion.json`, 72 scans, none of them test): keys are `viewpoint_id` or `viewpoint_id`+digit 1–4 (group members). There are 547 distinct anchors, with group sizes 1:420, 2:66, 3:47, 4:14. Fields are category `"<region_with_underscores>:<Activity_with_underscores>"`, index (glb variant 0:560/1:149/2:40, used as `category2idx[f'{category}_{index}']` in environments.py L183-192), and translation[120] / rotation[120] Euler degrees in the Habitat frame. I verified that Habitat (x, y_up, z) = MP3D (x, z, −y): the median xy distance between the frame-0 translation and the anchor viewpoint is 1.06 m with this mapping, against 8.2–17.8 m for the alternatives. The translation's y sits 0.84 m above the anchor floor (pelvis). 331 of the 486 HAPS-2.0 categories appear in the public 72 scans. The other 155 can only appear in test scans or nowhere, and their names are visible in the HAPS2_0 folder listing (one dir per `{category}_{index}`, environments.py L223-230).

## 6. How to build per-scan maps
**(A) Offline / privileged pipeline (needs MP3D approval; test-scan use = OFFLINE-ONLY, train/val use = COMPLIANT for training and evaluation):**
1. *Navmesh graph*: load `<scan>.navmesh`. Better, recompute with the scorer's settings (agent_radius 0.1, height 1.5, include_static_objects=True with humans; environments.py L134-139). Sample a 0.25 m lattice with snap_point/is_navigable and add edges where `try_step_no_sliding` reaches the neighbour. Weight edges with `distance_to_closest_obstacle` for clearance-aware (collision-free) paths. Anchor the R2R viewpoints: Habitat (x, y_nav, z) = MP3D (x, z_floor, −y). This is verified exactly for CE test starts (xz error median 0, max 0.5 m).
2. *Region map*: parse `.house`. (a) P-panorama records give an exact viewpoint→region index→label code. (b) For any continuous point, convert to MP3D (x, −z, y), pick the level whose bbox contains z, and run point-in-polygon on that level's region floor polygons (S/V CCW vertices) with z ∈ [floor, floor+height]; fall back to the nearest region AABB. (c) Portals (region0↔region1, span) give the room adjacency graph and door locations ("exit the bedroom", "go through the door on the left"). Without MP3D, the regcls labels give room types for 76% of test viewpoints. Propagate them to unlabelled nodes by nearest labelled neighbour on the same floor (inference).
3. *Object landmarks*: O records give OBB centers/axes/radii plus mpcat40/raw category → per-region object inventory and per-viewpoint visibility (raycast on the glb, or REVERIE BBox visible_pos, where view index i → heading 30°·(i mod 12), elevation −30/0/+30 for i//12 = 0/1/2). Without MP3D, approximate REVERIE object positions by intersecting rays from ≥2 viewpoints' bbox centres; the object ids are consistent across viewpoints.
4. *Human landmarks*: on train/val, use human_motion.json translation[frame] (Habitat frame) + category → region (2.0 region prefix matches MP3D ~95%). Test humans are not in public 2.0 data. The Phase-2 bundle must contain them for local rendering, if it ships at all, but README Q11 forbids reading them at inference. The 1.0 file is a weak prior (35% anchor overlap, ~1–4 m offsets).
**(B) Compliant online pipeline (PRIMARY):** build the same layers from egocentric RGB-D + GPS/compass.
- Occupancy/clearance from depth, with a 0.1 m agent radius plus margin.
- A room-type head trained on TRAIN-scan supervision: regcls train labels (5,943 panoramas / 35,658 single views) plus `.house` panorama→region for all 61 train scans after MP3D approval.
- An mpcat40 open-vocabulary detector/segmenter (supervised with train-scan `_semantic.ply`), projected into a top-down semantic map.
- A person detector + depth for human landmarks.
- A room-adjacency graph from detected doorways.
The test-scan statistics above (room composition, floors, humans) should only inform design choices; they must never be an input.

## 8. Facts vs inferences
**Verified facts** are listed in the JSON with evidence. **Inferences** (medium/low confidence):
- HA-R2R test start positions equal R2R-CE v1-2/v1-3 start positions (medium-high). The IDs and grouping match, but HA-R2R position data was not compared directly because HF is blocked.
- HA-R2R follows v1-3 headings (medium; config paths only).
- Expected ~161 test humans, 4.9–17.2 per scan by ratio scaling (low-medium).
- The .house panorama positions coincide with connectivity pose translations (medium; both come from the same Matterport capture, unverified without data).
- Label 9 merges porch and outdoor (medium).
- The regcls "unlabelled" set is mostly non-12-class rooms (medium; 75–81% of the 122 public 2.0 humans whose anchor viewpoint is unlabelled have a non-12 category; the rest are hallway 7, stairs 5, dining 4, others ≤2).

**Contradictions / corrections to other findings:** (1) A1 v1's "no public mirror of R2R-CE test.json.gz" is wrong. The v1-2 preprocessed file is public; A1 v2 has since corrected this independently and agrees with my ID-equivalence and ordering results. (2) A1 v1's "ascending path_id" order is wrong for test: 571/1,135 ascending pairs, scene-blocked per A1 v2. Because HA-R2R IDs equal R2R-CE IDs, the pose + text matching heuristic is unnecessary unless the bundle re-keys IDs; use episode_id → trajectory_id directly (A1 v2 says the same). (3) The brief's "30 region types": 29 rooms + junk (+ no-label). Nothing in CONTEXT.md facts 1–8 is contradicted. A negative result: start-to-nearest-human distance does not predict non-zero collision_num even with true 2.0 positions (val_unseen median 2.77 vs 3.04 m), so collision_num cannot be used to locate test humans from start poses.

## 9. Implications
- [COMPLIANT] Phase 2 is 1,136 trajectory problems whose structure is fully known now: scan, start viewpoint/pose, original R2R instructions (for offline analysis), and the candidate goal sets. Infrastructure (episode grouping, local replay harness, start-pose checks) can be finalised before Oct 30 without waiting for the bundle.
- [COMPLIANT] Room-type grounding of the instruction's final clause is the highest-leverage semantic cue. It shrinks goal candidates ~6× when the goal room is identifiable, and the instructions name it often (59–71% of paths across 3 instructions). A learned room classifier (trained on train scans) plus a top-down room map is worth building.
- [COMPLIANT] HA-R2R instructions carry HAPS-2.0 activity phrases whose region prefix matches the MP3D room label ~95% of the time on public scans. Parsing "a person ... cooking" → kitchen gives a second room cue, and the public 486-category library supplies the vocabulary.
- [OFFLINE-ONLY] With test-scan region labels, REVERIE objects and nav graphs, goal inference becomes ranking ~25 discrete candidates (≈4 after the room filter) with an LLM over 1–6 instructions, followed by collision-free planning on an inflated navmesh. The upside is very large, but it needs explicit organizer permission and would likely be judged privileged under the Oct-14 clarification.
- Training on test-scan annotations (regcls test labels, REVERIE test-scan boxes, R2R test instructions) would contaminate the "18 unseen buildings" evaluation. Do not do it in any regime.
